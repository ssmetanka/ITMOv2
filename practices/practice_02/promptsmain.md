2. RCTF (Role, Context, Task, Format)

Структурирует запрос по 4 обязательным осям: профессиональная роль, технический контекст, декомпозированная задача и жесткие требования к формату вывода.
Markdown

Прочитай исходный промпт и слабый артефакт из файла `[INPUT_FILE]`.

Преобразуй запрос, применив фреймворк **RCTF (Role, Context, Task, Format)**, и сгенерируй профессиональный артефакт:

1. **Role:** Задай релевантную инженерную роль (например, Lead Software Architect / Senior DevOps / Principal Security Engineer).
2. **Context:** Опиши технический стек, ограничения, нефункциональные требования (производительность, масштабируемость, безопасность).
3. **Task:** Сформулируй пошаговый перечень действий без двусмысленностей.
4. **Format:** Задай структуру артефакта (спецификация OpenAPI, класс с type hints, markdown-таблица, блок-схема Mermaid и т.д.).

3. CoV (Chain of Verification)

Генерирует черновик, формулирует верификационные вопросы для фактчекинга/поиска ошибок, независимо отвечает на них и выдает выверенную итоговую версию.
Markdown

Изучи исходный промпт и слабый артефакт из `[INPUT_FILE]`.

Примени технику **Chain of Verification (CoV)** для устранения галлюцинаций, архитектурных ошибок и пробелов в логике:

1. **Baseline Response:** Составь базовый расширенный ответ на задачу.
2. **Verification Questions:** Сформулируй 3–5 критических вопросов к коду/архитектуре (граничные условия, уязвимости, утечки ресурсов, соответствие стандартам).
3. **Verification Execution:** Ответь на каждый проверочный вопрос независимо, опираясь на лучшие инженерные практики.
4. **Final Verified Artifact:** Собери финальный артефакт, устранив все выявленные дефекты.

Запиши отчет и артефакт в файл `[OUTPUT_FILE]`:

## 1. Сконструированный CoV-промпт
(Инструкция модели для прохождения цикла верификации)

## 2. Протокол верификации
- Базовый ответ и найденные риски
- Проверочные вопросы и ответы на них

## 3. Итоговый верифицированный артефакт
(Финальный код / документ без найденных дефектов)

4. ToT (Tree of Thoughts)

Разветвляет процесс рассуждения на несколько независимых архитектурных/инженерных стратегий, оценивает их по критериям и выбирает наилучшую ветку.
Markdown

Проанализируй задачу и слабый ответ из файла `[INPUT_FILE]`.

Примени технику **Tree of Thoughts (ToT)** для поиска оптимального инженерного решения:

1. **Генерация мыслей (ветвей):** Предложи 3 принципиально разных подхода к решению задачи (например, разные архитектурные паттерны, алгоритмические подходы или библиотеки).
2. **Оценка состояний:** Оцени каждую ветвь по критериям: вычислительная сложность, читаемость, поддерживаемость, риски интеграции (шкала 1–10 с аргументацией).
3. **Выбор пути:** Выбери победившую ветвь или скомбинируй сильные стороны двух лучших.
4. **Финальная реализация:** Разверни выбранную мысль в полный артефакт.

Сохрани результат в `[OUTPUT_FILE]`:

(Промпт, инициирующий генерацию дерева альтернатив и дерева решений)

## 2. Дерево мыслей и сравнительная матрица
(Описание 3 альтернатив, критерии оценки, обоснование выбора победителя)

## 3. Реализованный финальный артефакт
(Полная реализация на базе выбранной ветви)

5. RAG (Retrieval-Augmented Generation / Grounded Prompting)

Имитирует RAG-пайплайн: изолирует внешнюю базу знаний/спецификацию в блок контекста и накладывает строгие правила генерации строго на основе предоставленных данных без домысливания.

Примени подход **RAG / Grounded Prompting**, смоделировав работу с проверенной базой знаний или официальной документацией:

6. ReAct (Reason + Act)

Организует пошаговый цикл решения задачи в формате Thought (рассуждение о текущем состоянии) -> Action (псевдовызов инструмента: линтер, тесты, поиск API) -> Observation (анализ результата) перед выдачей финального ответа.
Markdown

Прочитай слабый промпт и артефакт из `[INPUT_FILE]`.

Перепроектируй решение задачи через цикл **ReAct (Reasoning + Acting)**:

1. Составь промпт, который заставляет модель последовательно итеративно проходить шаги:
   - `Thought [i]`: рассуждение о следующем шаге реализации.
   - `Action [i]`: действие (симуляция запуска тестов, статического анализатора, запроса к БД или проверки граничных значений).
   - `Observation [i]`: полученный результат действия и выводы.
2. Пройди минимум 3 цикла Thought-Action-Observation для пошаговой сборки артефакта.
3. Сформируй итоговый ответ (`Final Answer`).
